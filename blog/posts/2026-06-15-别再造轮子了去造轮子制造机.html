# 别再造轮子了，去造「轮子制造机」

我们都听过「不要重复造轮子」这句箴言。于是我们熟练地 `npm install`、`pip install`、`go get`，把别人的轮子拼成自己的车。车跑起来了，但你有没有想过：**最厉害的不是会用轮子的人，而是造出「轮子制造机」的人？**

从「组装者」到「工具mith」

去年我重构一个老项目，发现代码里散落着 47 个处理日期、字符串、加密的工具函数。每个函数都写得挺好，但它们各自为政，没文档、没测试、没版本。新人来了，不敢动，只能再写一个 `formatDate2`。

后来我把这些函数提取成一个内部包，加上 TypeScript 类型、单元测试、语义化版本、自动化发布流水线。三个月后，这包成了团队标准件，甚至被隔壁组「偷」着用。

**区别在哪？** 区别不在代码质量，而在于是否建立了「生产工具的工具链」：类型系统守门、CI/CD 自动跑测试发版、语义化版本让升级无感、文档站随代码生成。这就是「轮子制造机」。

开源界的「制造机」长什么样？

  • **Vite / Turbopack**：不是打包工具，是「打包工具的编译器」。它们把「配置打包」变成了「写插件」。
  • **shadcn/ui**：不是组件库，是「组件库生成器」。`npx shadcn add button` 给你源码而非黑盒，你想改就改。
  • **Drizzle ORM**：不是 ORM，是「类型安全的 SQL 构建器生成器」。推断类型靠 TypeScript 编译器，不靠运行时魔法。
  • **Biome / Oxlint**：不是 Linter，是「用 Rust/Go 重写的、可扩展的、统一工具链制造机」。

    • 它们的共同点：**暴露原语，收敛复杂度，让使用者也能成为造轮子的人。**

    实战：把你的「偷懒脚本」变成团队基建

    别等有空再整理。下次写 `utils/` 里第 5 个工具函数时，顺手做三件事：

    1. **加类型**：哪怕只用 JSDoc，也让 IDE 能跳转、能报错

    2. **写一行测试**：`expect(fn(input)).toBe(output)`，覆盖最核心的 happy path

    3. **扔进 changeset**：`pnpm changeset` 生成变更日志，语义化版本自动走起

    坚持三个月，你的 `utils` 就长成了一个「微型轮子制造机」。新人入职第一天 `pnpm add @your-org/utils`，第二天就在用、在改、在贡献。

    结语

    世界不缺轮子，缺的是**让造轮子变得顺手、安全、可复制的元工具**。

    下次想 `npm publish` 一个 `left-pad` 时，先问自己：**我是在造轮子，还是在造造轮子的机器？**

    后者，才能跑赢时间。
