# 当AI会写代码，程序员还要「写」代码吗？

最近半年，我把 Cursor、Claude Code、Gemini CLI 全部接入了日常开发流程。原本需要半天的脚手架搭建、样板代码生成、甚至完整功能模块的实现，现在大多 10 分钟内搞定。

但越用越发现：我写代码的时间没少，反而多了。

从「手写」到「指挥」的认知偏移

以前写代码是「手工打磨」：每个变量名、每个边界条件、每个错误处理都要亲力亲为。现在是「意图表达」：我描述要什么，AI 给实现，我审查、修正、集成。

这看起来像效率提升，实则是认知负荷的转移。

**以前的认知链路**：需求 → 架构设计 → 接口定义 → 逐行实现 → 调试 → 重构

**现在的认知链路**：需求 → 意图拆解 → Prompt 设计 → 审查生成代码 → 集成测试 → 重构

后者看似更短，但对「系统性思维」要求更高。你必须一次性在脑子里跑通整个系统的数据流、边界、异常路径，才能写出精准的 Prompt 让 AI 一次性给对代码。稍有疏漏，AI 就会给你生成一个「能跑但有隐患」的实现，排查成本远超手写。

真正的护城河不在「写」，而在「判断」

GitHub Copilot 刚出时，大家担心「程序员会被取代」。用久了发现：AI 替代的是**确定性劳动**，保留甚至放大的是**不确定性决策**。

  • 选什么技术栈？AI 给不了上下文相关的权衡
  • 怎么切服务边界？AI 只会教科书式拆分，不懂业务演进
  • 这个 PR 有没有隐患？AI 只能找语法错误，找不出架构腐化
  • 重构时机到了没？AI 更倾向于「能跑就行」

    • 这些判断，依赖**上下文积累**、**业务直觉**、**吃过的亏**。AI 有知识，没有经验；有模式，没有直觉。

    我现在的工作流：做 AI 的「架构师」而非「打字员」

    1. **先写设计文档**（Markdown），把核心数据结构、接口契约、异常流程、测试用例全列出来

    2. **把文档喂给 AI**，让它按规范生成代码

    3. **我只做 Code Review**：检查边界处理、性能隐患、可维护性、与现有系统的契合度

    4. **发现问题回文档改**，再让 AI 重新生成，形成闭环

    这其实把「写代码」变成了「写规范 + 审代码」。代码成了规范的**副产品**，而非核心产出。

    给初中级工程师的建议

    别急着用 AI 生成代码练手。**先把「手写」练到能不看文档、不搜语法、不查 API 就能把中等复杂度模块写对**。建立扎实的代码直觉后，再引入 AI 做加速器。

    否则你会陷入「AI 生成 → 我不懂为什么这么写 → 出 Bug 我不会改 → 让 AI 改 → 依然不会」的死循环。那不是提效，是**外包了成长**。

    结语

    代码正在从「核心资产」变成「易耗品」。**会写代码不再稀缺，会决定写什么代码、怎么组织代码、何时重写代码，才稀缺。**

    下次打开 Cursor 前，先问自己：我清楚要什么吗？如果不清楚，合上编辑器，去想清楚需求再来。
