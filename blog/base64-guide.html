Base64 中文乱码与 URL 安全格式

Base64 编码的是字节，不是“文字本身”。中文出现乱码时，先检查编码与解码两端是否使用相同的字符集。

Tyler 工具箱 · 操作指南

先做一次往返测试

在Base64 编解码工具输入 你好，世界，点击“编码”，复制结果；再把结果粘回输入框，点击“解码”。如果恢复到原文，说明这条链路使用了相同的文本编码。本站工具会先把文本转为 UTF-8 字节，再执行 Base64 编码。

这也说明为什么直接把中文传给浏览器的旧式 btoa 函数可能报错：它处理的是单字节字符范围，中文字符需先转成字节。相反，解码后的字节也必须用相同编码还原为文本。

遇到乱码或“解码失败”时怎么查

  1. 确认输入的是完整 Base64 字符串，而不是带有 data:image/png;base64, 前缀的 Data URL。当前文本工具只接受编码主体。
  2. 确认它表示的是 UTF-8 文本。图片、压缩文件或其他二进制数据即使能解码，也不能直接作为文字显示。
  3. 检查复制过程中是否丢失字符、插入空格，或把 + 变成空格。表单和网址中尤其容易出现这种变化。
  4. 如果来源使用 GBK 等其他字符集，UTF-8 文本解码会产生乱码或错误。需要先确认来源的字符集，再选择对应的解码方式。

普通 Base64 与 Base64URL

普通 Base64 字符串可能包含 +、/ 和末尾的 =。Base64URL 通常把前两个字符替换成 -、_，并可能省略末尾填充。它们用途相近，但不能假设两种格式可以直接互换。

本站工具处理标准 Base64 文本。如果数据来自 JWT 或网址参数，应先确认上游要求的是哪一种格式；不能把 Base64URL 字符串直接当作普通 Base64 输入。网址中要传递普通 Base64 时，先对参数做 URL 编码。

Base64 不是加密。任何拿到字符串的人都可以解码。不要用它保存密码、令牌或身份证号，也不要把编码后的敏感信息当成安全分享方式。

什么时候适合用？

它适合在只接受文本的通道中携带字节数据，例如某些 API 字段或邮件附件格式。排查接口问题时，先问自己“原始内容是什么字节、使用什么字符集、接收方期待什么变体”，比反复尝试不同在线解码器更有效。
